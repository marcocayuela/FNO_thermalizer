# FNO_thermalizer
FNO + thermalizer

`src` contains all the necessary code to perform the experiment.

The folder `fno` contains the FNO-like architectures used in this experiment:
  - `fno_2D.py` implements the standard FNO architecture.
  - `fno_2D_classifier.py` implements the standard FNO architecture augmented with an additional classifier output.

The folder `training` contains all the tools and processes required to train the different models:
  - Emulator:
    - `fno_training.py`
    - `trainer.py`

  - Diffusion model:
    - `DiffusionModel.py`
    - `diffusion_training.py`
    - `trainer_diffusion.py`

  - Common utilities:
    - `factory.py`
    - `dataset_manager.py`
    - `metric_logger.py`

The data must be stored in a folder named `data` located at the root of the project.

The simulations can be generated using the KolSol solver available at:
https://github.com/MagriLab/KolSol

The generated simulations should be saved as `.h5` files in:

`data/kolmogorov/Re90/train_traj/`

to match the structure expected by `dataset_manager.py`. The KS-equation
pipeline (below) follows the same `data/KS_equation/nu<tag>/{train_traj,test_traj}/`
convention, generated by `KS_equation/1-D_periodic_Kuramoto_Sivashinsky_equation/generate_ks_dataset.py`
(sibling repo) instead of KolSol, with the field stored under the `"state"`
key (not `"velocity_field"`, which is specific to the 2D Kolmogorov data).

## Project layout (`src/`)

  - `entrypoints/` -- one `main_*.py` per (task x architecture) combination (emulator/diffusion x fno/wno/unet/hfno/ks), plus `main_diffusion_concat.py` for the Re-conditioned corrector.
  - `evaluation/` -- `correction_eval*.py` (autoregressive rollout with/without diffusion correction; `correction_eval_ks.py` is the 1D/KS counterpart), `plot_training_metrics.py`, `verify_diffusion_concat.py`, `test_emul_model.py` (manual sanity-check script, not a pytest suite despite the name).
  - `configs/` -- one `config_command_*.yaml` per entry point, all hyperparameters (architecture, training, data). `*_ks.yaml` = KS equation; `*_concat*`/`*_fno_hyper*`/`*_unet_*_2re*` = Re-conditioned diffusion corrector variants (trained across several Re/nu instead of one).
  - `scripts/` -- `run_*.sh` (training) and `submit_*.sh` (correction_eval), one per entry point, meant to be submitted via `sbatch`.
  - `fno/`, `training/`, `unet/`, `utils/`, `wno/`, `common/` -- shared model/training code imported by both `entrypoints/` and `evaluation/`. `fno/fno_1D*.py` are the 1D (KS) counterparts of `fno_2D*.py`; `fno/fno_2D_classifier_{concat,hyper}.py` and `training/diffusion_training_parametric.py` implement the Re-conditioned corrector (`common/param_conditioning.py::ParamEncoder`). `training/factory.py` (optimizer/scheduler/metric registries) and `training/diffusion_model_factory.py` (picks a diffusion backbone class by `model_type`) are unrelated despite the similar name.
  - `results/` -- output of `evaluation/*.py` runs (gitignored); `runs/`, `runs_mesu/` -- trained checkpoints, local and cluster-synced respectively (also gitignored).

## Running experiments

Each `run_*.sh` trains one (task x architecture) combination, reading its hyperparameters from the matching `configs/*.yaml`. Scripts must be submitted from within `src/` -- SLURM keeps the submission directory as the working directory, which is what makes the relative paths to `entrypoints/`, `configs/`, and `requirements.txt` resolve correctly:

    cd src
    sbatch scripts/run_emul.sh          # emulator, FNO       -> configs/config_command_emul.yaml
    sbatch scripts/run_emul_wno.sh      # emulator, WNO       -> configs/config_command_wno_emul.yaml
    sbatch scripts/run_emul_unet.sh     # emulator, UNet      -> configs/config_command_emul_unet_delta.yaml
    sbatch scripts/run_emul_ks.sh       # emulator, KS eq.    -> configs/config_command_emul_ks.yaml
    sbatch scripts/run_diff.sh          # diffusion, FNO      -> configs/config_command_diff.yaml
    sbatch scripts/run_diff_wno.sh      # diffusion, WNO      -> configs/config_command_diff_wno.yaml
    sbatch scripts/run_diff_unet.sh     # diffusion, UNet     -> configs/config_command_diff_unet.yaml
    sbatch scripts/run_diff_ks.sh       # diffusion, KS eq.   -> configs/config_command_diff_ks.yaml
    sbatch scripts/run_diff_concat.sh   # diffusion, Re-conditioned (multi-Re) -> configs/config_command_diff_concat*.yaml

To edit hyperparameters, edit the corresponding `configs/*.yaml` file rather than the script. The UNet emulator also accepts the config path as an optional positional argument (defaults to the delta-prediction config):

    sbatch scripts/run_emul_unet.sh configs/config_command_emul_unet_state.yaml

## Evaluating trained models (diffusion correction)

`evaluation/correction_eval*.py` roll trained emulators forward autoregressively, with and without diffusion correction, and compare against ground truth. Launch via the matching `submit_*.sh` (also from within `src/`):

    sbatch scripts/submit_correction_eval.sh          # FNO/WNO markovian emulators
    sbatch scripts/submit_correction_eval_unet.sh     # UNet emulator
    sbatch scripts/submit_correction_eval_seq_k5.sh   # sequence-to-one (k=5) emulators
    sbatch scripts/submit_correction_eval_ks.sh       # KS equation (evaluation/correction_eval_ks.py)

Key options are exposed as environment variables rather than being hardcoded (see the top of each `submit_*.sh` for the full list), e.g.:

    ROLLOUT=5000 SEED=101 DIVERGENCE_FACTOR=100 sbatch scripts/submit_correction_eval.sh

`correction_eval_ks.py`'s divergence detection is energy-threshold-based
(`--divergence_factor`, same mechanism as the 2D case) -- this works well for
Kolmogorov flow (a naive emulator becomes numerically unstable and blows up
to infinity) but KS is a bounded chaotic system: an inaccurate rollout can
decorrelate from the true trajectory while staying on a similar-energy
attractor, never triggering an energy-based threshold even after tens of
thousands of steps. If a KS rollout "never diverges" under
`--divergence_factor`, that's expected, not a bug -- switch to a GT-relative
error criterion instead (`evaluation/correction_eval.py::relative_l2_curve`
is already available and generic; `correction_eval_ks.py` doesn't use it yet).
